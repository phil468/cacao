# Anniversary Promotion

## Scope

Physical coupons are handed over with purchases, including web purchases. No digital codes are generated by checkout, payment confirmation, Izipay webhooks, or order transitions. Each valid registered code represents one entry. Winner selection is deliberately not implemented.

Local runtime now reads the MySQL connection from `backend/.env`, with an optional MySQL 8 Docker instance on `127.0.0.1:3307`. See the root README for startup. The former SQLite backend file remains a legacy data source/backup; it is not a mobile database. Automated tests still use disposable in-memory SQLite, independently from the local application connection.

The existing local data was transferred into MySQL 8.0.46 after creating a timestamped SQLite backup under `backend/storage/app/local-backups/`. All business-table row counts and declared foreign keys were checked during the transactional import. Sessions, cache, queued jobs, failed jobs, password-reset tokens and API tokens were excluded; sign in again after the switch. The original SQLite file was not modified. Local startup and admin access must now use MySQL, not the backup file.

The public entry point is `/promo`. A QR links to `/promo?code=ABC234`, using the application's configured URL. A query parameter only prefills the field; the server validates the code again.

## Data Model

- `promotions`: campaign identity, dates, amounts in PEN cents, activation and reviewed legal content.
- `promo_code_batches`: physical print batches, quantity, status and generating administrator.
- `promo_codes`: globally unique six-character uppercase codes, campaign, batch, registration, optional order and delivery timestamp.
- `promo_participants`: identity keyed by campaign and lowercase trimmed email; separate terms and marketing consent timestamps.
- `promotion_audit_logs`: generation, delivery, invalidation, batch disabling and export events, with actor and context.

Historical records cannot be deleted from Filament. Foreign keys protect registrations from accidental deletion. Codes use `random_int`, the alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, a global unique index and collision retries. This excludes 0/O, 1/I/L. Uppercase normalization also occurs in the model.

## Installation

Use PHP 8.2 with the existing Laravel extensions plus **GD**. GD is required to process the logo and verify coupon PDFs. Composer declares `ext-gd`, `barryvdh/laravel-dompdf ~3.1.1` and `chillerlan/php-qrcode ~5.0.5` directly; existing locked framework versions are preserved.

From `backend/`:

```bash
composer install --no-interaction --prefer-dist
php artisan migrate
php artisan db:seed --class=PromotionSeeder
npm ci
npm run build
```

`PromotionSeeder` is idempotent: it creates the initial campaign and grants `promotions.view` and `promotions.manage` to an existing `administrator` role. It does not overwrite configured dates or legal text. Full development seeding also invokes it. Do not run the full `DatabaseSeeder` to initialize this feature in production.

The initial campaign is **inactive** with no registration start/end dates. Its provisional draw date is October 28, 2026; all dates remain editable. The date-only seed is not an announcement of a draw time. Set the actual draw time before printing or activation.

## Administration

Under **Promoción Aniversario** in Filament:

1. Open **Promociones**, configure start, registration close and draw dates in Lima time, review the amounts (2000 cents per code), and replace every legal placeholder.
2. Confirm that the legal content has been reviewed and activate the campaign. Activation rejects incomplete dates, pending legal drafts and another already active campaign.
3. Open **Lotes de códigos**, choose **Generar lote de códigos**, enter a campaign, name and quantity (1–5000).
4. Download CSV or **Exportar cupones para impresión**. Exports require management permission and are audited. CSV excludes participant information and protects against spreadsheet formula injection.
5. Hand coupons over with purchases and record the handover using **Registrar entrega de código** or the POS receipt scanner. Search by order number or physical receipt reference. The order must be shipped/delivered and have no returns. Linking is idempotent and bounded by the products-after-discount amount, excluding delivery. This is a record of physical handover, not automatic issuance. Unissued historical codes cannot be registered simply because their activation label is **Anterior**. Explicit administrator-enabled courtesy codes remain supported without a sale.
6. Use **Auditoría de promociones** to inspect relevant events.

The dashboard displays generated/available/registered/disabled codes, unique participants, valid entries, today's code registrations in Lima time, and marketing-consent percentage. It uses the active campaign, or the most recent campaign when none is active.

## Printing

Each coupon is exactly **30 mm wide × 50 mm high**, vertical. A4 holds 30 coupons (6 columns × 5 rows) with 2 mm gaps and external cut marks. Each PDF request includes up to 150 coupons/five sheets; use part 1, 2, etc. for larger batches. Download the same part for both sides before registrations change its available-code list.

The reverse mirrors columns for **long-edge duplex** printing. Both files have matching page dimensions. Print at **100% / actual size**, with no fit-to-page. Run a physical front/back alignment and QR scanning check on the intended printer before printing the full batch. The layout has no bleed artwork; confirm stock and cutting requirements with the printer.

The editable template is `backend/resources/views/promo/coupons/sheet.blade.php`. Dimensions, gaps, margins and colors are in `backend/config/promotions.php`. The initial grid is designed for the required 30 × 50 mm size. The brand template remains subject to owner approval.

Disabled batches and disabled/registered codes are not offered as printable new coupons. Reprints do not create new codes or entries.

## Registration and Privacy

The registration transaction locks campaign, code and batch rows. A code must belong to the current campaign, be available and have an active batch. Dates, terms and identity are checked on the server. The code-to-participant assignment is permanent even after invalidation.

After successful registration, the server rotates the session identifier and stores the participant ID and codes proven in that browser session. Further codes require no repeated profile form. The public page displays only codes registered in that session and the participant's aggregate valid-entry count. It never lists a profile or historical codes based on a submitted email alone.

The same browser also sees a partially masked name, email and phone identifying
the information it submitted for the next code. These masks are not encryption
or identity verification. Only the masked summary is retained for display;
it is derived from that browser's successful initial submission, never read
from an existing participant profile found through email. A matching email
must not disclose another person's saved name/phone, even partially. Later
codes retain the summary and **Registrar para otra persona** clears it with the
participant/code session state. Older sessions without a summary show a neutral
notice rather than looking up and revealing stored identity. Existing registered
codes are neither invalidated nor reassigned automatically by this change;
administrators must explicitly audit/invalidate mistaken test registrations.

Local verification on 2026-10-17 confirmed that the reported local test code was already
registered with `activation_mode=legacy` but had no order, delivery timestamp or
activation timestamp. The read-only inspection did not alter that code or its
participant. New unissued legacy registrations are now rejected; existing
registration history is deliberately retained for explicit staff review.

A disposable SQLite/browser fixture (not the local business MySQL) verified

raw identity in the returned HTML, adding a second code, session reset and a
390px mobile layout. Initially validated locally, these changes were subsequently

An existing email does not authorize changing stored name, phone or marketing consent. Existing participant details remain unchanged. Email ownership verification and self-service consent/profile updates are not part of this release. Marketing is optional and never preselected; initial explicit consent and its timestamp are stored independently from mandatory terms acceptance.

Public submission uses CSRF, validation, a honeypot and an IP rate limit (10/minute and 60/hour). There is no external CAPTCHA provider. To add one later, extend `RegisterPromoCodeRequest` or a dedicated validation rule before invoking the registration service. Tune limits for shared networks after observing real use. Public promotion responses use private/no-store caching and no-referrer headers.

Use `/promo/terminos` and `/politica-de-privacidad` for editable legal text. `promotions:prepare-legal --apply` installs the conditions confirmed by the owner and deactivates the campaign for human review. It never changes campaign dates or participants. Repeated use overwrites editorial changes: do not execute it automatically on releases.

The 12-month period is the owner's chosen operational policy, not a universal statutory retention period. No claim is made that livestreaming substitutes an act, authorization or any other applicable draw requirement.

### Retention Operations

The approved 12-month period starts after the 15-day prize-claim window ends (Lima end-of-day). `promotions:anonymize` previews affected rows; `--apply` irreversibly removes name, email, phone, IP, browser and commercial consent from expired participant profiles, preserving code IDs and audit counts. It ignores active campaigns and campaigns with **Suspender anonimización por reclamo u obligación legal** enabled. The daily scheduler runs it at 03:30 Lima; Hostinger must actually execute `schedule:run`. Staff must deactivate closed campaigns, register/document necessary legal holds before expiry and remove holds promptly when justified. A hold is campaign-wide and must not be used to extend marketing.

Order/customer records are independent commerce data and are not erased by this job. Codes can remain linked to lawful order records; therefore remaining historic records are restricted, not claimed to be universally unidentifiable. Logs, exports, contact evidence, third-party copies and backups require a separate retention review. Do not restore expired personal data from a backup into operational use; reapply retention after any restoration. Do not collect identity-document copies unnecessarily. Requests to withdraw marketing or exercise rights are handled through the published email; no self-service withdrawal UI is included.

### Physical Sales and Camera Search

`/admin/point-of-sales` requires `orders.manage` and normal administrator-panel access. POS records are delivered, payment-confirmed orders with `user_id=null`, cashier ID, pickup snapshot and an optional receipt reference. Existing manual methods are available; `PointOfSaleSeeder` adds `pos_cash` idempotently without exposing it online. `payment_methods.is_available_online` is enforced by storefront/API options and checkout. This is payment recording, not integration with a card terminal or SUNAT invoicing.

`OrderLineService` is shared by web checkout and POS for locked stock checks, authoritative prices, immutable line snapshots and inventory movements. POS has a unique submission UUID and cashier lock to prevent double stock decrement on retries. Returns use the existing return service. Physical coupon recovery/invalidation remains an explicit operator action.

The code-list page requests camera access only after a click. It decodes QR frames locally using pinned `jsqr` 1.4.0 and sends only the scanned text to a permission-checked Livewire search method. URLs are parsed as data and never opened/fetched. Raw valid codes and `/promo?code=...` QR URLs are supported. Streams stop on detection, closing, hiding or navigation. Only the admin code-list response permits same-origin camera. Browsers require HTTPS or localhost; test on a real phone over the isolated HTTPS test environment. Permission denial and unsupported browsers retain manual table search.

See [test deployment](staging-deployment.md) for isolated Hostinger configuration and outstanding access requirements.

## Returns and Lost Batches

Recover the physical coupons when accepting returned purchases. Find each recovered code in Filament and select **Invalidar por devolución u otro motivo**, with a reason. Invalidation works for both available and registered coupons. Registered ownership and timestamps remain intact, but the code no longer counts in the draw. Do not recycle recovered coupons.

For partial returns, the operator must review the retained purchase value and recover the corresponding coupons. There is no automatic selection of which physical coupons a customer returns, and no change to the existing order-return service. Unlinked in-person coupons can also be invalidated by their printed code.

Disabling a lost batch invalidates its available codes and prevents further registration. Previously registered codes retain their status and ownership, but **the entire disabled batch is excluded from the draw query**. All these operations are audited; reactivation is intentionally unavailable.

## Draw and Future Messaging

`PromotionParticipationQuery::forPromotion()` returns registered codes with a participant, a registration timestamp within the configured window, and an enabled batch (if assigned). It excludes disabled codes and batches. Use this query for a future audited draw snapshot. No random winner selection, rankings or extra weighting are implemented.

`PromotionNotificationService` is a provider-neutral contract for future code/winner communications. It is not bound or automatically called in this physical-only release. Existing order email, WhatsApp, Telegram and push flows remain unchanged. No new `.env` variables are required.

## Production Release

Deployment requires explicit owner authorization. Enable GD on Hostinger first. After the normal release/migration procedure, run only:

```bash
php artisan db:seed --class=PromotionSeeder --force
php artisan optimize:clear
php artisan optimize
```

Then configure/review the campaign, verify public registration with controlled coupons and verify PDF output before activating. The existing local SQLite exclusion must remain in the production artifact workflow; never copy the development database.

## Rollback

For an operational rollback, deactivate the campaign and restore the previous application release. Keep promotion tables and records so registrations and audit history survive. Do not roll back a populated feature migration in production merely to disable the campaign.

For a disposable, verified-empty environment, the feature migration's `down()` removes only its five new tables in foreign-key order. A production schema rollback requires a separate reviewed backup/data-retention procedure; the existing commerce tables are untouched. Permissions may remain harmlessly installed after an application rollback.
